# v0.3 Design — Personal Knowledge Bridge

Status: **approved and implemented.** This document is the approved design and is
kept as the record of what was agreed. For what was actually built — including
the three deviations discovered during implementation — see
[`v0.3_implementation.md`](v0.3_implementation.md).

> Deviations found while implementing, all recorded in the implementation report:
> (1) declarations are committed through `observe()` (rules only), because running
> the LLM on top of an already-confident rule produced near-duplicates;
> (2) a declaration must be its own single-paragraph chunk, or Memory Core's rule
> extractor never sees `记住：` at the start of the text;
> (3) `learn()`/`observe()` gained a `provenance=` parameter, without which
> rule-derived memories could not carry `external_ref` / `document_title`.

---

## 1. v0.3 目标

让 Personal Memory Core 走出 CLI，进入真实的个人知识工作流。第一个消费者是
Obsidian。

```
Obsidian  (人类知识管理层)
    ↕
Personal Knowledge Bridge   (翻译层, 单向管线 ×2)
    ↕
Memory Core  (AI 长期记忆层, 仍是 Source of Truth)
```

**v0.3 只解决一个问题**：把「人写下的文本」和「AI 长期记住的断言」这两种不同的
东西，用一条受控的、可审计的、幂等的通道连接起来——**并且不制造第二个 Memory
数据库**。

v0.3 不增强检索算法，不引入 Agent/MCP/Web UI，不做后台自动学习。

---

## 2. 当前 v0.2 架构总结（作为设计前提）

| 事实 | 对 v0.3 的意义 |
|---|---|
| `memory.sqlite` 是唯一长期真相源（红线 1） | Bridge 不得持有任何独立状态文件 |
| `events` 表 append-only、不可变，memories 是派生视图（P0-3） | **文档应该以 event 形式进入，而不是以 memory 形式** |
| `Event.metadata` / `Memory.source` 是自由 JSON | **provenance 不需要 schema 迁移** |
| `Event.session_id` 是**已建索引的真实列**；`list_events(session_id=…)` 已存在 | 可作为导入幂等键，**无需迁移** |
| `learn()` = event → Candidate → validate → accept → commit | 文档导入直接复用这条管线 |
| `propose()` 完全无副作用（连 event 都不写） | 天然的 dry-run |
| `remember` / `learn` 是唯一受校验的写入闸门（红线 5） | Bridge 不得直写数据库 |
| `set_preference(..., source=)` / `set_project_state(..., source=)` 已接受 provenance | 结构化声明可走类型化 API，且不需要新接口 |
| `export_jsonl()` 只导出 SOURCE_TABLES，排除派生表 | 导出镜像不能作为真相 |
| `SCOPE_PREFIXES = (project, session, device, user, org)` | **没有 `persona`** |
| `recall(scope=None)` 搜索**全部** scope | ⚠️ **fail-open**，Persona 会互相泄漏 |
| Storage 不 import 模型 / HTTP；`retrieval/` 只用 provider 接口 + 可选 numpy | Bridge 必须遵守同样的纯度规则 |
| v0.2 测试：536 个用例，21 个模块 | 全部必须继续通过 |

## 3. Obsidian Bridge 架构

### 3.1 最重要的一个决定

> **Obsidian 的内容以 `events` 的形式进入 Memory Core，而不是以 `memories` 的形式。**

理由：

1. 它直接复用 P0-3 —— event 是不可变原文，memory 是派生断言。文档天然就是「原文」。
2. 它让 Bridge **在结构上无法**成为第二个 Memory 数据库：Bridge 只能追加剧历史，
   能不能变成记忆由 Core 的 Formation 决定。
3. 它让重新提炼成为可能：换一个提炼模型或策略，可以重放同一批事件（MSIT-3 的前提）。

### 3.2 分层

```
┌──────────────────────────────────────────────────────────────┐
│ Obsidian Vault  (人类的知识, 文件系统, 人类可自由编辑)          │
│   Notes/*.md    Projects/*.md    Daily/*.md                   │
└───────────────┬──────────────────────────▲───────────────────┘
                │ ① 只读扫描                │ ④ 生成镜像 (单向)
                ▼                          │
┌──────────────────────────────────────────────────────────────┐
│ memory_bridge/  (新包, 不属于 memory_core)                    │
│                                                              │
│  vault.py    只读扫描 + frontmatter + 排除规则                 │
│  chunker.py  标题切块 + content_hash                          │
│  classify.py 结构信号 + 显式标记 → 路由决策                    │
│  importer.py 幂等导入: 文档 → events → formation → memories    │
│  exporter.py memories → Markdown 镜像 (带 memory id 标记)      │
│  provenance.py  external_ref / hash / 字段规范                 │
└───────────────┬──────────────────────────▲───────────────────┘
                │ ② 只用公开 API            │ ③ 只用公开 API
                ▼                          │
┌──────────────────────────────────────────────────────────────┐
│ MemoryCore (api.py)  — 唯一读写门面                            │
│   learn() / propose() / recall() / set_preference() / ...     │
└───────────────┬──────────────────────────────────────────────┘
                ▼
        memory.sqlite  =  唯一长期真相源
```

**Bridge 只允许 import `memory_core.api`（以及 `memory_core.domain.dto`、
`memory_core.providers.base` 这类纯契约）。禁止 import `memory_core.storage`、
`sqlite3`、任何 provider 实现。** 由 AST 导入检查测试强制执行（见 §14）。

### 3.3 为什么 Bridge 是独立包而不是 `memory_core/` 的一部分

- Core 是「与消费者无关的基础设施」。把 Obsidian 概念（frontmatter、wikilink）
  放进 Core，等于把 Core 绑死在第一个消费者上。
- 独立包才能证明 Core 的公开 API 是**充分的**。如果 Bridge 做不到，那是 API 的
  缺陷，应该补 API，而不是让 Bridge 绕过它。
- 未来第二个消费者（Logseq、纯文件夹、浏览器书签、Agent）可以复用同一个 Bridge
  骨架。

## 4. 数据流

### 4.1 入站管线（Obsidian → Memory Core）

```
Markdown 文件
   │
   ├─(0) 排除规则: 导出目录 / .obsidian / 配置的 ignore globs
   │
   ├─(1) 计算 document_hash = sha256(规范化全文)
   │      └─ 已在 events 中出现过？→ 跳过整个文档 (0 写入)   ★ 文档级幂等
   │
   ├─(2) 按标题切块 → chunk[]，每块 content_hash = sha256(规范化块文本)
   │
   ├─(3) 分类 (classify) → 每块得到一个 route
   │
   ├─(4) 分流:
   │      ├─ route = knowledge/declaration
   │      │     record_event(kind, content=块原文, session_id=external_ref,
   │      │                  scope, metadata={provenance...})
   │      │        └─ learn(...)  → Candidate → validate → accept → memory
   │      │
   │      └─ route = preference / project_state  (结构化声明)
   │            record_event(同上, 保留原文)
   │              └─ set_preference(key, value, source={event_ids, provenance})
   │                 或 set_project_state(project_id, state, source={...})
   │
   └─(5) 输出报告: 新增/跳过/接受/拒绝 计数 + 每条 memory id
```

**关键点**：管线里没有任何一步允许 Bridge 直接构造 `Memory` 并写入。所有 memory
都必须是 `learn()` 或 `remember()` 的产物。

### 4.2 出站管线（Memory Core → Obsidian）

```
recall/list_memories/list_preferences/get_project_state   (只读 API)
   │
   ├─ 按 scope 分组
   ├─ 每条 memory → 一个带标记的 Markdown 区块
   │     <!-- memory id=mem_… kind=… confidence=… created=… source_ref=… -->
   │     用户正在开发名为 Persona-EdgeAIoT 的长期项目
   │     <!-- /memory -->
   └─ 写出 <vault>/AI Memory/<scope>.md   (整文件覆盖, 确定性排序 by id)
```

**出站是单向的、可丢弃的、可从 SQLite 完全重新生成的。** 没有 manifest 文件，
没有状态文件——标记就在 Markdown 里，所以镜像本身不构成第二个数据库。

## 5. 数据所有权

### 5.1 回答你的核心问题

> Obsidian 中的「我写下来的东西」和 Memory Core 中的「AI 长期记住的东西」
> 到底有什么区别？

**它们不是同一事物的两份拷贝，而是两种不同种类的东西。**

| | 我写下来的东西 | AI 长期记住的东西 |
|---|---|---|
| 单位 | **文档 / 段落**（连续文本） | **原子断言**（一个可独立判断真假的陈述） |
| 作者 | 人 | 系统（由事件 + 模型判断派生） |
| 权威 | **人**——人写什么就是什么 | **系统**——可从来源重建、可被取代 |
| 形态 | 完整、冗长、含个人行文/草稿/待办 | 精简、去重、带 confidence |
| 编辑 | 人随时自由重写 | 不覆盖历史，用 supersede 追加 |
| 生命周期 | 属于笔记，人删就删 | 属于记忆库，**删除来源不等于删除记忆** |
| 数量级 | 数千篇 | 数百条 |
| 检索 | 人搜索、链接、图谱 | AI 按 query 召回并注入 context |

一句话：

> **Obsidian 拥有「文本」。Memory Core 拥有「断言」。**
> Bridge 负责把文本翻译成断言，**不负责把断言翻译回文本的所有权**。

因此：

- **不是同步（sync）**。同步意味着两个地方都可以改、都要保持一致——那必然产生
  两个真相源。v0.3 是**两条各自单向的管线**：
  -  vault → events → memories（真相从人到 AI 流动）
  -  memories → markdown mirror（视图从 AI 到人流动）
- 镜像文件**不是可编辑的回写通道**。人改了它，下一次导出会覆盖；它不会被导入。

### 5.2 五类数据的归属

| 类别 | 存放位置 | 所有者 | 方向 | 说明 |
|---|---|---|---|---|
| **Human-authored Knowledge**（笔记正文、草稿、待办、链接） | Obsidian vault | **人 / Obsidian** | vault → Core（只读摄取为 events） | Core 永不修改 vault 中的原始笔记 |
| **Event / Provenance** | `events` 表 | **Memory Core** | 单向进；仅作为出处被引用 | append-only，永不删除 |
| **AI-derived Memory**（semantic / episodic / identity） | `memories` 表 | **Memory Core** | 单向出（生成镜像） | 这是「AI 记住的东西」 |
| **Explicit User Preference** | `preferences` 表 | **Memory Core** | 声明从 vault 进；镜像出 | 人在 vault 里*声明*，但偏好本身归 Core |
| **Project State** | `project_state` 表 | **Memory Core** | 声明从 vault 进；镜像出 | 同上；当前值只有 Core 能写 |
| **Vector Index**（派生） | `embeddings` 表 | 无（derived） | 不出 | 可删可重建，永不导出 |

**归属由「断言的种类」决定，不由「在哪里打字」决定。**
人在 Obsidian 里写下「我偏好深色主题」，那篇**笔记**归人；那条**偏好**归 Core。

### 5.3 明令禁止的模式

| 反模式 | 为什么禁止 |
|---|---|
| 把整个 vault 镜像进 memories | memories 会变成 vault 的第二份拷贝 → 两个真相源 |
| 把 memory 写回它来源的那篇笔记 | 人下次编辑就与 memory 冲突，无法判定谁对 |
| 让删除笔记自动删除 memory | 人会误删笔记；记忆不应因为文件操作而消失 |
| Bridge 维护 `.bridge-state.json` | 第二个持久化状态 → 违反红线 1 |
| 把导出的 Markdown 当可编辑源再导回 | 反馈循环 + 无限重复 memory |
| 让 Obsidian 直接查 SQLite | 绕过 Core 的校验与 scope 隔离 |

## 6. Provenance 设计

### 6.1 放哪里：`Event.metadata` + `Memory.source`（**无需 schema 迁移**）

两个字段都是自由 JSON，且都已经是「记录出处」的既有位置。

**Event 层**（每次摄取一个块写一个 event）：

```json
{
  "origin": "obsidian",
  "bridge_version": "0.3.0",
  "vault_id": "personal",
  "external_ref": "obsidian:personal/Projects/Persona-EdgeAIoT.md",
  "document_title": "Persona-EdgeAIoT",
  "document_hash": "sha256:9f2c…",
  "heading_path": ["项目状态", "当前阶段"],
  "line_start": 42,
  "line_end": 55,
  "content_hash": "sha256:41ab…",
  "mtime": "2026-10-03T09:12:44Z",
  "ingested_at": "2026-10-03T09:15:02Z",
  "route": "knowledge"
}
```

Event 行本身：`kind = "document"`、`role = "user"`、`content = 块原文（逐字）`、
`session_id = external_ref`、`scope = <目标 scope>`、`source = "obsidian-bridge"`。

**Memory 层**（由 Core 写入，Bridge 通过 candidate 的 `source` 传入）：

```json
{
  "origin": "obsidian",
  "external_ref": "obsidian:personal/Projects/Persona-EdgeAIoT.md",
  "document_title": "Persona-EdgeAIoT",
  "heading_path": ["项目状态", "当前阶段"],
  "content_hash": "sha256:41ab…",
  "event_ids": ["evt_01M3…"],
  "model": "ollama:qwen3:8b",
  "reason": "明确说明了当前阶段"
}
```

`event_ids` 已由 Core 自动补上（`_commit` 里 `source.setdefault("event_ids", …)`），
所以 Bridge 只需要传前几项。

### 6.2 `external_ref` 规范

```
obsidian:<vault_id>/<vault-relative-path>
```

- 稳定：重命名文件会改变它（这是对的——重命名是一次新的来源事件）。
- 可读：出问题时人眼能直接定位。
- 与 `session_id` 复用：**`session_id = external_ref`**，这样幂等查询可以直接用
  已被索引的 `list_events(session_id=…)`，不需要 JSON 查询、不需要新表。

### 6.3 必须保留的 6 个字段（你点名要求的）

| 要求 | 字段 |
|---|---|
| 文件路径 | `external_ref` + 其中的相对路径 |
| 文档标题 | `document_title` |
| source | `Event.source = "obsidian-bridge"` + `metadata.origin` |
| event id | `Memory.source.event_ids`（Core 自动填） |
| 时间 | `ingested_at`（摄取）+ `mtime`（文档修改时间）+ Core 的 `created_at` |
| scope | `Event.scope` / `Memory.scope` |

### 6.4 缺失/删除来源的处理

- 文档被删除或改到不再包含该块 → 该 memory 的 provenance 变为 **stale**。
- **默认只报告，不修改数据。** 绝不自动删除 memory（红线 7 的同类原则）。
- 可选（非默认）：`--mark-archived` 把 stale 记忆置为 `archived`（逻辑状态，
  仍可恢复、仍可查询历史）。
- 这保证「人的文件操作」不会毁掉「AI 的记忆」。

## 7. Deduplication 方案

三层，各管一件事：

### 第 1 层：摄取幂等（文档级 + 块级）——**防止重复 event**

| 层级 | 键 | 机制 |
|---|---|---|
| 文档级 | `(external_ref, document_hash)` | 先查该文档最近的 event；若已有相同 `document_hash`，整篇跳过（0 event） |
| 块级 | `(external_ref, content_hash)` | 文档变了才逐块比对；只有新块/改动块产生 event |

实现：`store.list_events(session_id=external_ref, limit=N)`（**已存在的 API**，
`session_id` 已有索引），在 Python 里比对 `metadata` 中的 hash。**无 schema 变更、
无需 JSON1 扩展。**

预期效果：对未改动的 vault 反复 import → 第二次 0 新 event、0 新 memory。

> 规模注记：单文档 event 数随编辑次数增长。文档级短路让常见情况（未改动）只查
> 一次。若将来单文档 event 数上千，再引入一张 `sources(external_ref, content_hash,
> event_id)` 表作为优化——届时是一次小型、纯增量的 v4 迁移，现在不做。

### 第 2 层：记忆级去重——**防止重复 memory**（**已有能力，直接复用**）

- `AcceptancePolicy.dedupe`：同 scope 内规范化内容完全相同的候选 → 拒绝
  （reason: duplicate）。
- LLM 提炼时 `_formation_context()` 已经把最相关的既有记忆放进 prompt，模型可以
  选择 NOOP 而不是 ADD。
- 规则式显式声明（`记住：`）走 confidence 1.0 的确定性路径。

### 第 3 层：跨文档语义重复——**明确不解决**

同一个事实写在两篇笔记里，会产生两条语义等价的 memory。这是**已知限制**：

- 不引入向量近邻去重（会把 Bridge 变成检索系统，且需要调阈值）。
- 缓解：LLM 在 context 里看到相似记忆时倾向 NOOP。
- 诊断工具（后续、可选）：`memory-bridge duplicates --report` 只读报告，不自动合并。

### 第 4 层：导出回环防护

- 导出目录（默认 `AI Memory/`）**默认加入 import 排除列表**。
- 即使人把它重新纳入导入范围，块内的 `<!-- memory id=… -->` 标记会让导入器识别
  出「这是导出镜像」，直接跳过。
- 双保险，确保 export → import 不会无限增殖。

## 8. Scope / Namespace 方案

### 8.1 现状与问题

```
SCOPE_PREFIXES = ("project", "session", "device", "user", "org")
```

- 没有 `persona`。
- 更严重的是：`recall(scope=None)` **搜索所有 scope**，`Retriever._keyword_hits` /
  `_semantic_hits` 只在 `scope is not None` 时才过滤。

这意味着：**一旦引入 Persona，persona A 的私有记忆会被 persona B 的默认检索读到。**
这是一个 fail-open 的默认值，必须修。

### 8.2 建议的最小改动（**v0.3 唯一需要动 Core 的地方**）

**改动 1 — 词表（1 行）**

```python
SCOPE_PREFIXES = ("project", "session", "device", "user", "org", "persona")
```

`require_scope` 的正则 `^[a-z][a-z0-9_]*:[A-Za-z0-9][A-Za-z0-9._:-]*$` 已经兼容
`persona:aria`，无需改。

**改动 2 — 可见性（约 30–40 行，跨 storage / retrieval / api）**

新增「可见 scope 集合」概念，并采用 **fail-closed** 默认：

| 调用方式 | 可见范围 |
|---|---|
| `recall(q)` （不指定） | 除 `persona:*` 以外的全部 scope ← **默认排除 Persona** |
| `recall(q, scopes=["global","project:x"])` | 恰好这些 |
| `recall(q, persona="aria")` | `persona:aria` + `global`（+ 显式给出的 project） |

具体实现：

- `storage.search_memories(..., scopes=None, exclude_prefixes=None)`
  → SQL 增加 `scope IN (…)` 与 `scope NOT LIKE 'persona:%'`。
  同样加到 `search_preferences` / `list_memories` / `list_preferences` /
  `list_project_states`。
- `Retriever.recall(..., scopes=None, persona=None)` 负责把 persona 展开成可见集合。
- `MemoryCore.recall(..., scopes=None, persona=None)` 透传。
- `learn()` / `propose()` 的 formation context 也必须用同一套可见性——否则
  persona B 的记忆会通过 prompt context 泄漏给 persona A。**这一点容易漏，必须
  一起改。**

**向后兼容**：现有所有调用都不传 `scopes`/`persona`，行为变化仅仅是「不再返回
`persona:*`」——而 v0.2 数据里根本没有 `persona:*`，所以 **536 个测试应当全部
原样通过**。

### 8.3 明确的能力边界（必须诚实写进文档）

这是**同一个数据库内的策略隔离**，不是密码学隔离：

- 它防止「忘记传 scope 导致跨 persona 读取」这类**意外泄漏**。
- 它不防止有人直接打开 `memory.sqlite` 或直接调用 storage。
- 如果将来需要**强隔离**（不可信 persona、多用户、外包执行），需要独立数据库或
  加密——**v0.3 明确不做**，并记录再引入触发条件（见 §15）。

### 8.4 Bridge 如何分配 scope

优先级从高到低：

1. frontmatter `scope: project:persona-edgeaiot` → 直接用（经 `require_scope` 校验）
2. frontmatter `persona: aria` → `persona:aria`
3. frontmatter `project: persona-edgeaiot` → `project:persona-edgeaiot`
4. Bridge 配置的路径映射：`Projects/<name>/**` → `project:<name>`
5. 兜底 → `global`

**scope 由 Bridge 决定，memory 由 Core 决定。** Bridge 只把 scope 当参数传给
`learn(scope=…)` / `set_preference(scope=…)`。

## 9. Obsidian → Memory 流程（详细）

### 9.1 分类：如何区分五类内容

分类发生在 **Bridge**，产出一个 `route`，然后交给 Core 已有的两条路径处理。

| 内容类型 | 判定信号（确定性优先） | route | 走哪条 Core 路径 |
|---|---|---|---|
| **普通知识 / 笔记** | 默认 | `knowledge` | event → `learn()`（LLM 判断，多数应为 NOOP） |
| **用户明确声明** | 块内含 `记住：` / `记住:` / `remember:` / `> [!memory]` callout | `declaration` | event → `learn()`（规则提取器命中，confidence 1.0） |
| **项目状态** | frontmatter `type: project-state` + `project: <id>`，或块内含 `项目状态：<id> = {json}` | `project_state` | event → `set_project_state(..., source=…)` |
| **用户偏好** | frontmatter `type: preference` + `key/value`，或块内含 `偏好：k = v` | `preference` | event → `set_preference(..., source=…)` |
| **可长期记忆的知识** | 无显式标记，由 LLM 判断是否 durable | `knowledge` | event → `learn()` |

**设计立场（重要）**：

> **默认应该是保守的：大多数人类笔记不应该变成 memory。**

一个 vault 有几千篇笔记。如果每篇都变成记忆，记忆库会被用户自己的写作淹没——
这是「把 Obsidian 变成第二个 Memory DB」的另一种失败形态。所以：

- 无标记的普通笔记 → 走 LLM 判断，**预期大量 NOOP**。
- 只有「明确声明」和「LLM 认为 durable」的内容才产生 memory。
- 导入**默认 dry-run**（见 §9.3），人先看计划再决定。

### 9.2 为什么结构化声明不走 LLM

偏好与项目状态是**精确的键值/当前值**，Core 自己的架构立场就是「不让概率模型写
preference / project_state」（architecture.md §10、ADR 0006）。所以 Bridge 对它们
走**类型化 API**，不经过 LLM：

```
record_event(块原文, metadata=provenance)      # 保留原文与出处
set_preference(key, value, scope, source={"event_ids":[evt_id], **provenance})
set_project_state(project_id, state, scope, source={...})
```

两个 setter 都已经接受 `source=`，**不需要任何新 API**。

### 9.3 幂等与可审查

- **默认 dry-run**：`memory-bridge import <vault> --dry-run`
  用 `propose()` 产出计划（`propose()` 连 event 都不写），打印表格：
  文件 / 块 / 路由 / 提议内容 / 是否接受 / 理由 / 预计 scope。
- **执行**：`memory-bridge import <vault> --apply`
  真正走 `record_event()` + `learn()` / 类型化 setter。
- 两者之间 LLM 会跑两次（`propose` 一次、`learn` 一次）。这是可接受的代价：
  计划是**建议性**的，幂等性由 event 层保证，而不是由候选内容保证。
  （若将来觉得重复调用昂贵，可加一个 `MemoryCore.apply(candidates)` 把已校验的
  候选直接提交——**列入 v0.3 之后的可选增量，不在本次范围**。）

### 9.4 chunking 规则（确定性、可复现）

1. 按 Markdown 标题切分（`#`..`######`），保留 `heading_path`。
2. 单块超过 `max_chunk_chars`（默认 2000）时按空行二次切分。
3. 小于 `min_chunk_chars`（默认 40）的块丢弃（标题、分隔线、空段落）。
4. 代码块、frontmatter、dataview 代码块**默认不参与形成**（可配置）。
5. `content_hash = sha256(normalize(块文本))`，`normalize` 只做换行与首尾空白归一，
   **不做语义改写**——同样的文件必须得到同样的 hash。

## 10. Memory → Obsidian 流程（详细）

### 10.1 输出布局

```
<vault>/AI Memory/
    _README.md                  # 说明「这是生成文件，编辑无效」
    global.md
    project-persona-edgeaiot.md
    persona-aria.md
```

一个 scope 一个文件（而不是一条记忆一个文件），避免制造几千个小文件。

### 10.2 文件格式

```markdown
---
generated: true
generator: memory-core-bridge 0.3.0
source: memory.sqlite
scope: project:persona-edgeaiot
exported_at: 2026-10-03T09:20:11Z
memory_count: 3
---

> ⚠️ 本文件由 Memory Core 自动生成。**在这里的编辑不会被记住**，下次导出会被覆盖。
> 要修改记忆，请编辑它的来源笔记并重新导入，或使用 `memory-core` CLI。

<!-- memory id=mem_01M3Y8GSNP4GG5X3GSJ7KJPG1B kind=semantic confidence=0.95
     created=2026-10-02T12:13:12.758Z origin=obsidian
     source_ref=obsidian:personal/Projects/Persona-EdgeAIoT.md -->
用户正在开发名为 Persona-EdgeAIoT 的长期项目
<!-- /memory -->
```

### 10.3 必须满足的四条要求（你点名要求的）

| 要求 | 如何满足 |
|---|---|
| 不破坏 Source of Truth | 导出是纯读操作；不写任何 manifest/状态文件；删掉整个 `AI Memory/` 目录不影响任何东西 |
| 导出不成为第二个 Memory DB | 没有独立状态；标记在文件内；**默认从导入中排除**；`_README.md` 明确标注为生成物 |
| 保留 memory id / provenance | 每个块带 `id` / `kind` / `confidence` / `created` / `source_ref`（HTML 注释，阅读视图不可见但机器可读） |
| 可再次导入而不无限重复 | ① 默认排除该目录；② 即使纳入，标记识别 → 跳过；③ 即使都没有，内容 hash 也会被记忆级去重拦下 |

### 10.4 为什么不做「Obsidian 里改记忆然后回写」

因为那会立刻制造第二个可写真相源，并引出无法自动解决的冲突（AI 说 A，人说 B，
谁对？）。v0.3 明确：**镜像不可回写**。要改记忆，改来源笔记重新导入，或用 CLI。

## 14. 验收测试设计

每组测试对应一条红线或一条设计承诺。

### A. 幂等性

| # | 测试 | 断言 |
|---|---|---|
| A1 | 同一个 vault 连导两次 | 第二次新增 event = 0，新增 memory = 0 |
| A2 | 只改一个 section 后重导 | 只有该块的 event 增加；其他 memory 的 id/内容完全不变 |
| A3 | 导出后再导入（导出目录未排除） | 新增 memory = 0（标记识别生效） |

### B. Provenance 完整性

| # | 测试 | 断言 |
|---|---|---|
| B1 | 每条 bridge 来源的 memory | `source.external_ref` / `document_title` / `content_hash` / `event_ids` 均非空 |
| B2 | 每条 bridge event | `metadata` 含 6 个必需字段（§6.3）；`session_id == external_ref` |
| B3 | 从 memory 反查到源文件 | `external_ref` 能定位到真实存在的文件（存在时） |

### C. 数据所有权与边界

| # | 测试 | 断言 |
|---|---|---|
| C1 | 删除来源笔记后重导 | **memory 数量不变**；报告里出现 stale 标记 |
| C2 | 导入是只读的 | vault 内所有文件的 mtime/content 不变 |
| C3 | 编辑导出的镜像文件后重导 | 不产生新 memory；下次导出覆盖该编辑 |
| C4 | vault 里有 1000 篇普通笔记，其中 3 篇带显式标记 | 产生的 memory 数量远小于 1000（保守默认）；3 条显式声明全部入库且 confidence=1.0 |

### D. Scope 与隔离（关键安全属性）

| # | 测试 | 断言 |
|---|---|---|
| D1 | `recall(q)`（不指定 scope） | 结果中**没有任何** `persona:*` |
| D2 | persona A 写入的记忆 | persona B 的 `recall(q, persona="b")` **查不到** |
| D3 | persona A 的 formation context | persona B 的 `learn()` prompt 里**不含** A 的记忆 |
| D4 | `recall(q, persona="a")` | 能看到 `persona:a` + `global`，看不到 `persona:b` |
| D5 | 全局记忆 | 所有 persona 都能看到（global 是共享层） |

### E. Bridge 纯度（架构红线）

| # | 测试 | 断言 |
|---|---|---|
| E1 | AST 扫描 `memory_bridge/**` | 不 import `memory_core.storage`、`sqlite3`、任何 provider 实现、`urllib`/`http` |
| E2 | 只允许的 import 白名单 | `memory_core.api`、`memory_core.domain.dto`、`memory_core.domain.errors`、`memory_core.providers.base` |
| E3 | 无第二个持久化文件 | 运行 import/export 后，除 `memory.sqlite` 外项目目录无新增文件 |

### F. 与 v0.2 红线的回归

| # | 测试 | 断言 |
|---|---|---|
| F1 | 原有 536 个测试 | 全部通过 |
| F2 | MSIT-1 / MSIT-2 | 在有 bridge 来源数据的情况下仍然通过 |
| F3 | 删除整个 vector index 后 | bridge 来源的 memory 一条不少、可关键词检索、可导出 |
| F4 | 无模型环境（无 Ollama） | `export`、`status`、关键词 `recall` 全部可用；`import --apply` 明确降级并报告 |
| F5 | `--dry-run` | 数据库文件 SHA256 **逐字节不变** |

### G. 确定性

| # | 测试 | 断言 |
|---|---|---|
| G1 | 同一文件切块两次 | 块数、边界、`content_hash` 完全一致 |
| G2 | 同一数据库导出两次 | 输出文件逐字节相同 |

## 15. 未来 Persona / Agent / AIoT 的扩展点

这一节只记录**已经预留好的接缝**，v0.3 不实现任何一项。

| 方向 | 现在已有的接缝 | 未来需要什么 | 再引入触发条件 |
|---|---|---|---|
| **Persona** | `persona:` scope + fail-closed 可见性（v0.3 建立） | Character Card UI、persona 级 default scope、跨 persona 共享策略 | 当你真的同时运行第二个 persona 时 |
| **Persona 强隔离** | 单库多 scope 是**策略隔离** | 独立 `memory.sqlite` 或字段级加密 | 出现不可信 persona / 多用户 / 外包执行 |
| **Agent** | `MemoryCore` 公开 API 已经是完整能力面；Agent 只是另一个 Consumer | Agent 侧的编排（可能是 LangGraph） | Agent 需要多步状态机时。**Agent 永不拥有记忆**（红线 1 的推论） |
| **AIoT / 端云** | `device:` scope 已存在；**`events` 是不可变的同步单元** | 边缘节点同步 *events*，记忆在中心形成 | 第二个物理设备要写入同一份记忆时。同步 events 而不是 memories，天然避免冲突 |
| **其他知识库**（Logseq / 纯文件夹 / 浏览器书签） | `Bridge` 骨架（vault 扫描 / chunk / classify / import / export） | 只替换 `obsidian/` 子包 | 出现第二个真实消费者时——那时才能判断抽象是否正确 |
| **检索质量评估** | `docs/benchmarks.md` 的方法论 | 标注语料 + IR 指标 | 需要调整 RRF 权重或换 embedding 模型时 |
| **ANN 索引** | `VectorIndex` 接口 | 实现一个新 `VectorIndex` | 向量 p95 > 50 ms（10k 条时 13.4 ms，还很远） |
